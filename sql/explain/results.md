## What the load felt

p99 is over the operations (single statements) that finished in the window. Worst second is the highest one-second p99, which also counts operations still waiting, so a stall shows even when nothing completes. A stalled second is one in which an operation had waited 500 ms or more. The last column is the strict test: p99 at most twice the baseline, no errors and no stalled second. The lesson asks for it only of the safe migration (step 3); for the others read max ms and stalled seconds.

## Step 3: the safe migration

- Forced conflict: with a long read open, the safe `ALTER` (lock_timeout 1 s) failed after 1.00 s (failed fast: True). It still held up the load for that second: a failed attempt queues too, so the timeout is also the longest stall a retry can cause.
- Add column: 1 attempt(s). Backfill: 1013 batches of 2,000 rows with a 0.05 s pause, 83 s in all; rows still NULL afterwards: 0.
- Bloat: table 194 MB before, 392 MB after the backfill (344,474 dead row versions): every updated row is a new version.

## Step 4: the index

- Plain `CREATE INDEX`: built in 0.8 s; the load's slowest operation took 692.6 ms (baseline max is a few milliseconds), because inserts and updates waited for the build.
- `CREATE INDEX CONCURRENTLY` interrupted on purpose: cancelled = True, invalid indexes found = ['idx_events_device_created']. Dropped, rebuilt in 1.0 s with 0 load errors and a slowest operation of 129.9 ms; valid after rebuild: True.
